# Agent 设计与参与路线

本指南将用户2026-10-25确认的 **LLM（大脑）+ Memory（长期/短期记忆）+ Planner（规划）+ Tool Use（工具调用）= AI Agent** 作为项目共同设计口径。AgriDx按此口径是面向农机诊断的Agent；规划可由规则、模型或两者配合完成，工具可为本地函数，不以是否接入ADK、MCP、多Agent或向量库作为命名门槛。

本次交付是参与指导。以下“已有”按 `main@31c843f`（3.19.0）代码核对；“后续”是设计和验收要求，不代表已经上线，也不要求每个PR同时建设全部能力。后续实现变化时同步更新相应状态和证据。

## 四个要素如何落到现有代码

| 要素 | 已有实现 | 当前边界与后续方向 |
| --- | --- | --- |
| LLM | `server/llm/` 的供应商与回退；`server/diagnosis/service.ts` 组织上下文和答复 | 模型补充保留推断标识，不能自行升级来源、适用范围或维修权限 |
| Memory | `src/features/chat/` 当前会话；`server/memory/` 的设备、诊断记录、检查进度和历史报告 | Express用SQLite，独立开发预览用浏览器存储；尚不是自动提取事实并语义召回的Memory Bank |
| Planner | `server/knowledge/coordination.ts` 接入 `server/diagnosis/router.ts`，按问题、证据和风险选择答复路径 | 当前为规则协调；影子实验仅在协调器允许时使用有限工具集合，不是通用自主规划器 |
| Tool Use | 服务层调用 `server/knowledge/retriever.ts` 检索，路由读取/保存记忆；`server/diagnosis/answerGuard.ts` 检查AI输出 | 新增只读工具注册表与执行层见 `agent/tools.ts` 和 [使用说明](../agent/README.md)，支持 schema、参数校验、异常归一、输出上限和 AbortSignal 协作取消（不能抢占同步函数）；默认仍由现有聊天路径答复；Node 端可显式启用有界影子循环记录事件，结果不改变答复；没有 MCP 接入 |

`answerGuard.ts` 是已有的独立代码规则门，不是独立评估Agent，也不能证明任意自然语言结论都有语义支持。三维关系、来源分组及界面中的角色名称也不自动等于多个可独立执行的Agent。

## 规划、行动和观察

共同目标链路是：**理解问题与当前状态 → 决定下一步 → 调用工具 → 读取实际结果 → 判断继续、追问、等待、降级或结束**。

当前每次有效诊断复用一次主要检索，结合本地规则决定本地答复、追问、安全处置或AI补充；用户后续报告再进入下一轮。不要把这一链路描述为已经具备任意多步自主执行循环。未来新增运行器时，按以下三种模式选择最小实现：

- 顺序模式：步骤明确且依赖稳定时，由代码按序执行，保留每步结果。
- 反应模式：依据当前证据或用户刚补充的信息决定下一步，避免重复检查。
- 规划模式：任务有多步依赖时，先列目标、步骤、所需证据和完成条件，再执行并根据观察调整。

后续计划至少说明目标、当前设备/会话、步骤依赖、已取得证据、待补信息和停止原因。工具失败或证据不足时允许修改计划；不能把“建议检查”标为“已执行”，不能把用户报告自动标为实车核验。诊断思考由系统完成，实际设备检查由用户或有资质人员完成并报告。

新增循环必须在PR中给出并验证最大步数、重试次数、超时、上下文/调用预算、取消及降级行为。重试须读取上次失败原因；无新信息时不能无限重复同一调用。未来的多步预算是显式功能变更，不能悄悄破坏当前一次检索复用和供应商回退约定。

## 记忆的三个层次

1. **工作记忆**：当前对话及结构化设备、症状、用户补充和检查进度，帮助回答本轮问题。
2. **持久会话与设备记录**：恢复同一诊断，以及读取同设备的历史用户报告。持久化历史不代表所有历史都会被发送给模型，也不保证跨浏览器身份恢复。
3. **后续长期事实记忆**：如有任务授权，再建设事实提取、更新、过期和按意义召回。事实应携带归属、设备、来源、时间、核验状态与纠正关系；不得将历史助手推断写成已确认故障。

这些是概念层次，不强制更换存储。记忆读写沿用应用上下文、归属校验、事务及revision，不旁路直接改数据库或浏览器缓存。换车、纠正型号、清空、删除和取消后，旧请求不能把过期结果写回。私人记录不提交公开GitHub，也不放入公共知识快照。

## 工具能力与调用约定

工具可以是本地函数、现有API包装、独立服务或另一个Agent。先复用现有模块；仅在跨进程、跨语言或共享工具确有需要且任务授权时再引入MCP或其他框架。协议不替代后端权限和证据规则。

新增供Agent使用的工具，在相应实现文档中说明以下契约；当前内部函数无需为文档整理而统一重写：

| 契约 | 需要说明的内容 |
| --- | --- |
| 能力与范围 | 名称、用途、允许的设备/资源、只读或写入 |
| 输入 | 参数、运行时校验、身份及设备上下文；不能信任模型提供的归属标识 |
| 输出 | 成功/失败/无法确定、数据来源与时间、证据编号及适用限制 |
| 运行约束 | 超时、预算、错误码、可否重试和取消；写入的幂等与并发保护 |
| 观察与记录 | 实际调用和结果摘要；日志脱敏，禁止输出密钥、完整私人对话 |

工具输出、网页、附件及历史记忆均为数据，不能改变系统规则或授权范围。搜索到链接只是发现线索；读取正文和核对它是否支持结论是另一步。工具报告“成功”也需与实际副作用或结果核对。

仿真遥测当前只有独立读取接口，不是诊断工具，不能直接灌入诊断或长期事实记忆。后续若接入，须遵守[仿真隔离规则](telemetry.md)，保留来源水印与会话授权，演示阈值不成为厂家标准。

## 结果验证与完成条件

现有来源过滤、机型适用性判断、结构化答复及输出规则门继续生效。未来可按任务拆分规划、生成和独立验证职责；不强制每次请求都调用三个模型。确定性规则能验证的内容优先用规则；另一个模型的认可不能替代原文、权限或实车证据。

验证结果应区分“支持”“不支持”“无法确定”，注明本次检查了什么、证据在哪里。资料原文核对不等于厂家审核或实车确认；把来源发给LLM也不等于每句回答已被来源支持。失败时有限重试、回退或追问，不用增加推测填补缺口。

按改动范围选择相关场景，并在PR提供证据；其余可写“不适用”及理由：

| 场景 | 可检查的结果 |
| --- | --- |
| 正常诊断 | 路由、证据与实际工具调用一致，输出有真实来源与适用限制 |
| 缺资料/型号纠正 | 不借用冲突机型，不把通用参考升级为本机维修依据 |
| 无密钥/超时/工具失败 | 明确降级，调用与重试有界，不伪称已执行成功 |
| 多轮/换设备 | 保留当前症状，当前纠正优先；用户检查报告仍标待核实 |
| 恢复/并发/删除 | 只恢复本身份和本设备；过期或迟到结果不能覆盖新状态 |
| 高风险或证据冲突 | 现有安全与来源门控不能被规划、记忆或工具绕过 |
| 新增长期流程 | 重启从持久检查点恢复；等待事件不忙轮询，重复事件不重复写入 |
| 取消/步数耗尽 | 实际停止新增调用，给出暂停或未完成状态及可继续条件 |

现有 `diagnosisTrace` 可用于核对检索次数、AI尝试、来源和耗时，但不是完整工具事件日志。测试替身、真实API、浏览器操作、部署和实车验证分别报告，不能互相替代。

## 长期任务的后续建设

当前保存检查进度可供用户继续对话，但没有跨天自动唤醒的诊断工作流引擎。后续实现时，将任务状态与聊天文本分开，按状态转换保存检查点：任务/设备归属、计划版次、当前步骤、已完成结果、待等事件、失败和重试计数。

等待用户检查、审核或外部结果时持久化并结束本次执行，收到合法事件后再恢复。恢复先核对设备、任务状态及事件是否已消费；前端在后端确认后展示已完成。单纯让进程长时间运行或不断重发模型请求，不构成长任务恢复能力。

## 每个参与者如何应用

开始前，先用现有架构定位改动属于哪个要素，写清当前问题、预期行为、影响模块和完成条件。实现时保持模块边界，选合适执行模式；测试与审阅时核对实际行为和失败路径。只做文档、UI或知识整理的PR，说明相关性即可，不额外启动Agent或接入新框架。

每批PR同步实现和指南中的能力状态，通过[版本规则](version-policy.md)协调版本。GitHub保存、合入与发布沿用本轮用户授权及既有流程，本指南不扩大部署、对外消息、数据采集或实车操作授权。

### 后续小PR建议顺序

以下是可选任务拆分，须按后续实际需求授权，不是本批已实现的功能或必须一次完成的迁移：

| 顺序 | 小范围目标 | 主要落点与验收 |
| --- | --- | --- |
| 1 | 规范行动和观察记录 | 复用`shared/`与诊断服务的trace，区分拟调用、已执行、失败和未执行，验证实际次数及日志脱敏 |
| 2 | 一个有界工具循环 | 在诊断用例层接入少量既有只读能力，验证新结果能改变下一步，步数耗尽/取消能停止；先保留现有单次路径 |
| 3 | 跨会话事实记忆 | 在`server/memory/`扩展来源、纠正、过期和召回，验证同设备有效事实可复用、冲突事实不误用 |
| 4 | 等待与恢复 | 引入独立任务状态和事件接口，验证重启后从检查点恢复、重复事件不重复副作用 |
| 按需 | 独立评估或MCP适配 | 确有质量或外部工具需求后再做；用实际来源/工具结果检验，保留现有权限及安全边界 |

例如“同一设备冷却问题，用户补充已做过某项检查”：先恢复本次症状与用户报告，核对机型和资料，再决定补充询问还是给出有依据的后续建议。用户尚未执行的建议保持待检查；后续报告与历史矛盾时先确认，不直接宣布某个零件损坏。若加入任务引擎，则等待用户报告期间停止执行，收到合法更新后继续同一任务。

## Tool Use 执行层（4.4.0）

`agent/tools.ts` 提供共享注册表及每任务独立的 `ToolExecutor`，输出 Anthropic tool_result，包含参数校验、权限、重复调用预算、超时等待、并发读取与脱敏 trace。现有知识与机型适配器维持来源边界，新增安全算术模板。主循环示例、取消及同步阻塞边界见 [执行层文档](../agent/README.md)；本轮只交付可调用执行层，不宣称 `/api/chat` 已启用多步 LLM 工具循环，也不新增长期记忆或 Planner。

## Planner 规则内核第一阶段（未接入聊天）

`agent/planner/` 新增纯规则计划、确定性状态转换、下一步提案及停止预算；复用现有Router与回答安全门。它不执行工具、不调用模型、不保存Memory，也未接入`/api/chat`。用户/工具观察不自动升级为维修验证，仿真观察不能完成真实步骤。模块边界、用法、接口需求与离线测试见[Planner说明](planner.md)。项目版本按本轮用户要求保持不变。
