# 知识库治理流程：先审再写

> 计划《AgriDx 知识库下一步整理计划》第 2 步的落地文件。只管“新增资料怎么进库”的流程，
> 不改知识事实、不改四层分离（原件 / 来源记录 → `sources.json` → 人读知识卡 →
> `entries.jsonl` → `hierarchy.json`）、不改《条目整理规范.md》与《知识库/AGENTS.md》的
> 15 条核验规则、不改图谱派生规则、不动 `archive/*`、不改工作流 / 服务器配置 / 密钥 / 权限。
> 改动计划模板见 [知识库/模板/改动计划模板.md](../知识库/模板/改动计划模板.md)；
> 已填好的示例见 [知识库/改动记录/2026-11-06-示例-沃得雨刮器开关去重.md](../知识库/改动记录/2026-11-06-示例-沃得雨刮器开关去重.md)。

## 一、六步流程

新增资料必须按顺序走完六步，未通过前一步不进入下一步；未通过校验不合并进 `main`。

| 步骤 | 做什么 | 输入 | 输出 | 通过条件 |
| --- | --- | --- | --- | --- |
| 1. 采集 | 按《条目整理规范.md》“国内使用机型的采集顺序”核对统计 / 报道正文，定向找精确适用的手册，选页目视核验 | 原件或来源记录、公开入口 | 来源记录（`path` / `url` / `sha256` / `bytes` / `verified_pdf_pages`） | 封面、正文型号、后缀、市场 / 排放、配置、版次已核对；冲突留待核实，不猜 |
| 2. 去重 | 新条目与已有 `entries.jsonl` / 知识卡全文比对，疑似重复写入去重评审 | 新条目草稿、已有条目 | `dedup-review.jsonl` 中的一对判定 | 每对疑似重复都有 `pair_id`、`decision`（`keep` / `supersede`）、判定理由与判定人；见第二节 |
| 3. 出改动计划 | 按模板写改动计划：新增 / 改 / 删哪些条目、影响哪些品牌 / 机型 | 去重判定、来源与页码 | `知识库/改动记录/YYYY-MM-DD-<主题>.md` | 计划里每一条都能追到 `source_id` + 页码；见第三节 |
| 4. 人审 | 人工审改动计划（不是审脚本输出） | 改动计划 | 人审结论（通过 / 打回 / 局部通过）与签字 | 来源、页码、适用范围、去重判定、回滚办法、图谱检查项六项全过才算通过；打回的项写清原因，不写库 |
| 5. 写库 | 按通过的计划写库，不多写、不改计划外条目 | 通过的改动计划 | 更新后的 `sources.json`、`entries.jsonl`、知识卡、`hierarchy.json`、`kb-version.json` | 只改计划列出的文件与行；见第五节 |
| 6. 跑校验 | 校验与测试全过才合进 `main` | 写库后的工作区 | 校验与测试结果 | `python3 知识库/工具/校验索引.py` + `npm test` + `npm run build:server` + `npm run verify` 全过；健康计数核对见第六节 |

## 二、去重规则（复用既有判定口径）

- 去重先看适用范围再看文字：同一知识在不同机型 / 不同手册范围内的变体，**分别保留**，
  不判重复。既有判定例：`DP-120d381daf8d2ed4`（约翰迪尔 5E 与 6B 保养间隔分级，
  `decision: keep`）、`DP-c33f1452a19fa964`（阿波斯 P5000 与欧豹 TB 交机培训，
  `decision: keep`）。
- 只有同一事实、适用范围实质相同、且较新来源已覆盖较旧来源时，才判 `supersede`。
  既有判定例：`DP-e3c857fd407966c6`（沃得雨刮器开关操作，2021 条目被 2022 条目取代，
  `decision: supersede`，判定人昶捷，2026-10-21）。
- `supersede` 是“标记”，不是“删除”：被取代的条目行保留在 `entries.jsonl` 与知识卡中，
  只加取代标记（见第五节），检索与展示是否排除由人审在改动计划里定，不静默删行。
- 每对疑似重复的判定都要写进 `dedup-review.jsonl`：`pair_id`、双方 `entry_id`、相似度、
  `ai_verdict`（仅供参考）、`decision`、`reason`、判定人、`decided_at`。AI 建议不代替人判。

## 三、改动计划（先出计划，人审后再写）

每批新增先写一份改动计划，存放在 `知识库/改动记录/`，文件名
`YYYY-MM-DD-<主题>.md`，模板见 [知识库/模板/改动计划模板.md](../知识库/模板/改动计划模板.md)。
必填内容：

1. **批次与基底**：批次 ID、基底 `main` 提交 SHA、知识库版本（`kb-version.json` 的 `kb_version`）。
2. **新增 / 改 / 删表**：每行一个 `entry_id`（新增用拟用编号，不可复用已有编号），
   写清 `source_id` + 章节 / 表号 + PDF 物理页 + 印刷页、标题、品牌 / 型号、
   `entry_type`、适用条件与 `scope_boundary`。
3. **影响范围**：影响哪些品牌 / 机型、哪些知识卡文件、是否动 `hierarchy.json`、
   是否动 `通用框架.json`。
4. **去重依据**：每条新增 / 改的疑似重复对写 `pair_id` + `decision` + 理由；
   无疑似重复的写“无疑似重复，已比对”。
5. **合并方式**：新内容如何合并进已有知识卡（见第四节），不覆盖旧条目。
6. **回滚办法**：按第七节写清删哪些索引行、恢复哪个文件版本。
7. **图谱同步检查项**：按第八节逐项勾选。
8. **人审栏**：审阅人、审阅时间、结论、打回原因（若有）。

验收硬线：**改动计划里每一条都能追到来源和页码**—— `source_id` 必须存在于
`sources.json`，页码必须能在知识卡证据行与原件选页中找到，找不到的条目不写库。

## 四、合并，不覆盖（借 Arkon 的做法）

- 新内容合并进已有知识卡，不覆盖旧条目：新事实追加新的 `## 条目编号｜标题` 段；
  旧段原文不动、不改写、不删节；旧 `entry_id` 不复用、不改指到新内容。
- 同一机型的相近事实分别保留（例如不同配置、不同排放、不同版次的同类操作各留一条，
  各自标明适用条件），不在改动计划里把它们“合并成一条”。
- 被取代的旧条目：在旧知识卡段后追加一行取代说明（写清被哪个 `entry_id` 取代、
  依据哪个 `pair_id` 判定、判定日期），旧段正文保留可查；新条目卡段追加一行
  “取代说明”（写清取代了哪个旧 `entry_id`）。
- 故障表原因仍只算候选，不直接确诊；整理者补充的限制标明“整理边界”，不冒充厂家原句。

## 五、写库：写哪些文件，怎么写

按通过的改动计划写库，只改计划列出的文件与行：

- `sources.json`：新来源一个 `source_id`，字段按《条目整理规范.md》“来源字段”表；
  同一 PDF 被多个机型页引用时去重，不重复登记。
- `entries.jsonl`：每行一个 JSON 对象，只存定位、标签和适用元数据，不存第二份事实正文；
  不得用 `summary` 保存事实概述（校验工具会拒绝该字段）。
- 知识卡：人读正文只在 Markdown 维护，`## 条目编号｜标题` 与索引编号 / 标题一致。
- `hierarchy.json`：增删正式条目或改变适用范围时同步维护品牌 → 机型 → 组件 → 零件
  导航关系，人工核对组件 / 零件关联；没有具体零件证据时只到组件。
- `通用框架.json`：原关联条目删除或正文改变时同步核对阶段及文字依据。
- `entry-roles.jsonl`（旁路）：`roles` / `role_basis` / `risk_level` / `risk_basis`
  改存于此，不直接写 `entries.jsonl`；`原文标记` 须逐项核对正文字段标签。
- `kb-version.json`：写库后用 `node scripts/kb-version.mjs --bump`
  重算 `content_hash`，并按 `YYYY.MM.N` 递进 `kb_version`（同月递增、跨月重置；
  不带 `--bump` 只做核对，不写文件）。
  内容变了而 `kb_version` 没升版时，`tests/kb-version.test.mjs` 会拦截。
  注意：这是知识库版次，不是项目版本；项目版本按 `docs/version-policy.md` 另行协调，
  本流程不自动升项目版。
- 改动计划文件本身在人审通过后补记执行结果（实际提交 SHA、校验结果、回滚记录），
  与该批提交一同保存到 GitHub。

## 六、跑校验与验收

写库后、合进 `main` 前，从仓库根目录执行：

```bash
python3 知识库/工具/校验索引.py
npm test
npm run build:server
npm run verify
```

- 校验工具检查来源哈希、字节数、页数、唯一编号、源引用、标题定位、证据页范围和类型；
  工具不会下载原件或修改索引。
- 重新加载服务，查 `/api/health` 的 `archivedEntries` 是否等于 `entries.jsonl` 行数，
  再按品牌 / 完整型号实际问答一次，确认编号、版本、页码和边界出现在答案中。
- 任一校验或测试未通过，不合并；修好后重跑全套，不只跑单项。

## 七、改动记录与回滚

- 每批留一份改动记录（`知识库/改动记录/YYYY-MM-DD-<主题>.md`），与该批提交一同进 GitHub。
  记录 = 改动计划 + 人审结论 + 实际提交 SHA + 校验结果 + 回滚办法。没有改动记录的批不合入。
- 回滚办法必须写到“不看人也能执行”的程度，至少包括：
  1. **删哪些索引行**：列出本批新增的 `entries.jsonl` 行号 / `entry_id`、新增的
     `sources.json` 的 `source_id`、新增的 `hierarchy.json` 行（`entry_id` + 组件 / 零件）。
  2. **恢复哪个文件版本**：被改的旧条目行、旧知识卡段、旧 `hierarchy.json` 行、
     旧 `kb-version.json`（`kb_version` 与 `content_hash`）恢复到哪一次提交的哪一个版本
     （写清提交 SHA，不写“恢复到之前”）。
  3. **执行方式**：首选 `git revert <该批提交 SHA>`（保留历史，不改写已合入历史）；
     若该批提交之后已有后续提交压在其上，改用一份反向改动计划逐项恢复，再按第五节重算
     `kb-version.json`。
  4. **回滚后验证**：重跑第六节全套校验 + 健康计数核对，确认计数回到回滚前。
- 禁止用 `force-push` 改写已合入 `main` 的历史来“回滚”；禁止只删 GitHub 上的文件而不留记录。

## 八、图谱同步衔接（分类 / `hierarchy.json` 变化时）

图谱没有第二份数据：服务端 `server/knowledge/snapshot.ts` 在加载时从当前
`entries.jsonl` + `hierarchy.json` + `通用框架.json` 整体重建知识快照，
图谱页与 `/#/knowledge` 目录都读同一份快照。因此治理流程只覆盖检查项，
**不另存第二份图数据，不改图谱派生规则**（派生规则的改动是计划第 1 步的范围）：

- [ ] 本批是否改了 `hierarchy.json`（新增 / 删除 / 改适用范围的行）？若改了，列出受影响的
      `entry_id` 与组件 / 零件路径。
- [ ] 本批是否增删了品牌 / 机型 / 组件 / 零件分类？若有，同步检查 `通用框架.json` 的关联
      是否同步更新，分类名与 `hierarchy.json` 是否一致。
- [ ] 图谱随快照整体切换：写库后重建快照，确认图谱页节点与 `/#/knowledge` 计数、
      `/api/health` 计数三处一致；不接受“只改了图谱文件、快照还是旧的”状态。
- [ ] 排除项照旧：千寻位置节点继续排除（2026-11-01 的排除决定），不借改动计划放回图谱展示。
- [ ] Graphify 导出（`npm run knowledge:graphify`）是快照的导出物：`hierarchy.json` 变了，
      旧导出文件作废，须重新导出；不复用旧导出文件冒充新图谱。
- [ ] 被取代（`supersede`）的条目：`hierarchy.json` 中的对应行是否保留 / 移除，
      由人审在改动计划里定并写清理由；不默认删除，也不默认保留——必须显式决定。

## 九、不改什么（重申计划第四节）

- 不改四层分离，不存第二份事实正文。
- 不改核验规则：选页目视核对、PDF 物理页 vs 印刷页、型号 / 排放冲突留待核实、不跨机型补造参数。
- 不改适用性硬过滤：指定品牌 / 型号只查匹配归档，不用通识补位；未指定时归档 + 通识统一排序，通识标清楚。
- 不把 LLM 抽取、向量召回、社区报告的输出当成已验证事实；故障表原因仍是候选。
- 不动 `archive/*`，不改工作流、服务器配置、密钥、权限；不直接推 `main`，不升项目版
  （项目版本按现有规则另行协调）。
- 不引 AgriKG 的百科 / Wikidata 内容进诊断。
