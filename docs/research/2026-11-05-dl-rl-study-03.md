## 一、强化学习 / 智能体架构方向：DeepSeek Super-agent——Router + Worker + Watchdog

- 标题：Exploring Super-agent Design: Towards a More Autonomous Agent System（DeepSeek Harness 团队设计文章，2026-11-01）
- 原型仓库：deepseek-ai/dsh-superagent-prototype（2026-10-31 发布，MIT 许可，单 commit；本次抓取时约 19026 星）
- 链接：https://github.com/deepseek-ai/dsh-superagent-prototype
- 设计文章链接：原文发于 X / 微信公众号长文，本次未直接读到原文；设计细节来自 explainx.ai 的二手梳理（https://explainx.ai/blog/deepseek-super-agent-architecture-router-worker-triggers-watchdog-2026），另有 Medium、redreamality、dev.to、AgentsPulse 的多篇二手解读互相印证。原型仓库的 README 与 docs/000-philosophy.md、docs/003-execution.md、docs/007-architecture.md 为本次一手读到。

### 核心设计（原文结论；设计文章部分为二手转述，见“阅读边界”）

1. **问题诊断**：编码智能体单任务所需的人力帮助在减少，瓶颈转移到了**人的注意力**——一个人通常只能同时跟进 3–5 个活跃会话。单会话的问题是 ReAct 一次一步、不同任务互相污染上下文、本地设备离线则一切停止；每事件一会话的问题是结果互不关联、多个会话各自回复用户。
2. **Super-agent 的四特质**：连续（Continuous，在任何渠道都像同一个 agent）、高产（Productive，多任务并行、不等上一个完成就接新指令）、主动（Proactive，监听环境、值得处理才行动、其余时间保持安静）、持久（Persistent，一直在线、接入真实工作环境、能自行从故障中恢复）。
3. **五模块**：① 两层架构（Router + Worker）；② 事件驱动 Trigger；③ 全双工多通道交互；④ 计算、状态、环境分离；⑤ Watchdog。
4. **Router 层（只分发、不执行）**：长驻会话，接收全部渠道的人类输入，是系统的“全局定序点、协调点与记忆”。为避免成为瓶颈，它**不执行任务**，“可以完全不用 Bash 工具”。Router 的工作比预想的简单，通常用较轻的模型就能兼顾速度与质量。Workers 不直接对人说话，所有回复由 Router 写出，工具日志与推理过程不进群聊。
5. **Worker 层（隔离、最强模型）**：每个 Worker 拥有一个任务、隔离的上下文与完整工具集；因为 Worker 决定每个结果的质量，通常需要最强的模型。Worker 默认互不通信；当两个 Worker 触及同一个 PR 时，各自订阅该 PR 的事件流，自行解决冲突。Worker 自己也可以用 subagent 或组成 agent 团队，Router 不需要知道。
6. **Trigger 与两级过滤**：主要输入不再是 typed prompt，而是半结构化事件流（群聊消息、邮件、日历提醒、代码评审意见、CI 结果）。处理分四步，按顺序：① **代码先过滤（快路径）**：按来源、群组、用户/bot 白名单做程序化策略，每个来源可设“只响应明确请求 / 作为候选事件 / 忽略”；② **语义策略（慢路径）**：通过的事件交给 LLM，按提示词写成的策略判断；③ Thread 订阅直通；④ 推测执行。
7. **Thread 订阅（follow-up 不过 Router）**：同一 PR、同一聊天主题、同一邮件链上的连续事件构成一个 Thread。Router 为 Thread 的首个事件创建 Worker 后，该 Worker **订阅**这个 Thread；之后的新事件由代码直接递给 Worker，不再经过 Router 决策。订阅是多对多：一个 Worker 可跟多个 Thread，一个 Thread 可有多个 Worker；超出任务范围的事件 Worker 可以退订或交还给 Router。原型实现中这对应 Engine 的 Subscription 与 `handback` 机制。
8. **上下文当缓存：Inline / Spill 与 Chain of Recall**：借用编译器术语——Inline 把接下来可能需要的信息直接放进窗口，Spill 把其余部分留在窗口外、只留一个 ID 或简短摘要。“浪费上下文窗口就是浪费模型的智能。”每个 Trigger、Thread、Worker Session 都有 ID，每个被召回的对象内联与其相连对象的 ID 与摘要，模型沿着这些链接一次一跳地展开，想走多远走多远。这就是 **Chain of Recall**：Router 不需要把全部历史塞进窗口，也能在几天后、换个渠道被问起旧任务时恢复上下文。
9. **全双工异步工具**：经典 ReAct 的同步 `run()` 会阻塞整个会话直到返回。DeepSeek 把长调用换成 `start()` / `stop()`：`start()` 立即返回 "Started"，完成结果稍后作为新事件到达；模型可以对运行过久的命令调用 `stop()`。新输入在“当前推理步结束时”就得到处理，而不必等后台工具完成。原型实现中：Executor 的 shell 命令 5 秒后转后台作业；后台工作每轮结束后最多 30 分钟，超时则杀掉作业并报告等待。
10. **计算、状态、环境分离**：Agent Loop 跑在无状态云容器里，会话存在数据库中，容器可重启、可扩容而不丢失；仓库、凭证与硬件留在原地，每台机器跑一个轻量 daemon，“不保存会话状态，只执行命令并返回结果”。这针对 BYOM（Bring Your Own Machine）场景：个人开发机只在部分时间在线，重连后云端 agent 继续排队等它的任务。
11. **Watchdog**：独立于主系统的 agent 会话，由定时消息驱动。它处理 API 错误、状态恢复等基础设施故障；更重要的是**用模型判断每个 Worker 是否在取得真实进展**，而不只是进程是否还活着（“进程还在跑，但模型卡在无产出循环里或已偏离目标，存活探针看不到”）。因为它本身就是完整 agent 会话，维护者可以用自然语言问它某事为何失败，或让它在系统运行时改提示词与触发规则。
12. **原型实现的关键机制（一手读到，docs/003-execution.md 与 docs/007-architecture.md）**：
    - Engine 是 Trigger、Thread、Decision、Ticket、Assignment 的唯一写入者；所有命令同步执行、每命令一个事务；端口在事务内排队外部工作、提交后由适配器执行。
    - Ticket 阶段表（自上而下首个匹配行胜出）：person/delivery（Input 投递失败，按 2 秒、翻倍至 1 分钟退避重试）、person/answer（有待回答的 Attention）、person/review（最新报告为 ready）、person/blocked 或 failed、working/queued（无 Assignment 或待启动）、idle（最新报告为 waiting 或 Assignment 已结束）、working（其余）。
    - 并发槽位有上限，另留 1 个额外槽位给人类消息或状态请求；新工作不能挡住人继续已有 Ticket。
    - 失败重试：瞬时故障（HTTP 408 / 429 / 5xx、连接被拒/重置/超时）先重试 3 次、退避递增；失败的 prepare 命令不重试；失败的启动不自动重试。
    - 重启恢复：运行中的 Assignment 以 "host restarted" 结束，新 Assignment 带 recovery note（先查目录、git 历史与 GitHub，再重复任何外部动作），按最旧 Ticket 优先。
    - 自动合并默认只允许：为本 Ticket 开的 PR、已 ready、所需审批覆盖 head commit、增删合计少于 200 行；推送新修订前先撤回自动合并。
    - 理念（docs/000-philosophy.md，一手）：**一切按注意力成本衡量**——消息、通知、问题、设置、面板元素、一段文档都要付出大于成本的价值，否则删掉。Agent 只在被问到、或团队书面规则允许时行动；只在人必须行动或能用上结果时说话；一次问一个具体问题；**按影响停止，而不是按努力停止**（本地改动做到可评审的结果为止，需要设计决策的改动以明确问题停止）；诚实报告（草稿标为未完成、失败报为失败、绝不绕过限制以免提问）。未被请求的工作先以“只记录会做什么”的模式启动。
13. **实验（原文结论，二手转述；作者自称结果“仅供参考”）**：合成负载，每轮约 300 条群聊与 GitHub CI 消息，其中约 20 个是工作请求，其余是聊天、追问、取消与 CI 噪声；编码用只耗时间的模拟工具代替，测的是调度而非编码能力。Super-agent：任务时间 p50 12.4 分钟 / p95 15.7 分钟，每轮缓存读取 token 23.2M；单会话 + subagent 工具（中性提示）：20.4 / 29.5 分钟，6.1M；单会话 + subagent（委派优先提示）：13.8 / 29.0 分钟，10.8M；去掉直通的 Super-agent：12.6 / 15.5 分钟，31.8M。三个发现：① **提示词不是可靠的委派开关**——中性提示下 5 次运行模型一次也没调用 subagent，强委派提示下 5 次有 4 次委派、第 5 次因判断工作“小”而自己做并拖出长尾；两层设计取消了这个选择（Router 不能执行）；② **用 token 换时间**——Super-agent 的缓存读取 token 约为单会话设计的 2–4 倍；③ **直通省 token 不省时间**——去掉直通后 Router 决策多约 30%、token 多约 37%，但任务时间不变。Router 压力测试（只跑 Router、Worker 用 mock）：需要决策的 Trigger 从约 1/分钟升到约 40/分钟时，平均批大小从 1.0 升到 2.8，每请求耗时仅从 2.5 秒升到 3.9 秒，摊到每个决策上从 6.4 秒降到 1.6 秒——单个 Router 随负载上升反而更便宜，直到上下文与准确率上限。
14. **开放问题（原文结论，二手转述）**：扩展（何时分片 Router、Worker 何时直接对话未定；运行数月后长期记忆成为主要限制）；无会话的产品形态（一个屏幕上的聊天不再对应一个会话时，人如何查看与指挥任务）；上下文边界与 A2A（哪些团队共享一个 Super-agent、不同权限的 agent 如何安全对话）；**安全与隐私**（事件驱动引入更多不可信输入；若云端 Agent Loop 被入侵或提示注入攻破，每个相连的端点设备都可能被接管；凭证需要“agent 能用但永远看不到”的使用方式）。

### 与 AgriDx Agent 的直接相关（推断为主，逐条标注）

- **Memory 长期记忆（推断）**：Chain of Recall 是 PR #209 长期记忆草案之后最值得抄的召回形态。AgriDx 的长期记忆若按“整段晋升文本塞进上下文”做，几次晋升就会挤占诊断窗口；改成“每个诊断会话 / 证据对象带稳定 ID，召回时只内联摘要 + 下一跳 ID，模型按需逐跳展开”，既保留跨会话连续性，又控制 token。这不需要多会话架构，是提示词 + 存储格式层的改动。
- **Planner 与跨轮调度（推断）**：Thread 订阅思想直接对应 AgriDx 的缺口——目前主循环是 8 秒预算、4 步、同轮去重、无跨轮调度。同一诊断会话的后续追问（同一 Thread）应当直通到已确认的主题与证据集合，而不是每轮重新匹配一次主题、重新检索一遍。GAP 的 DAG 解决的是“一次诊断内的并行”，Thread 订阅解决的是“多轮之间的复用”，两者互补。
- **Tool Use 工具协调（推断）**：两级过滤（代码快路径在前、模型慢路径在后）可以补到 AgriDx 的工具调用之前：allowlist / 预算 / 去重这些确定性规则先由代码判定，只有通过的才交给模型决定是否调用，减少无效调用与 token 浪费。异步工具（5 秒转后台、30 分钟上限）对应 AgriDx 的 8 秒预算：长检索不应阻塞主循环，而应以后台作业 + 新事件唤醒的方式处理；但 AgriDx 是单次问答场景，异步的收益小于常驻 agent，优先级低于看门狗。
- **Watchdog 看门狗（推断）**：这是本次对 AgriDx 最直接、最便宜的一条借鉴。AgriDx 目前只有 8 秒超时这一种“存活”判断，没有“进展”判断。可以加一条不依赖新训练的规则：同一主题重复检索、或连续两轮没有产生新证据，即判定为“无进展循环”，停止并降置信度、转人工，而不是继续烧 token、烧轮数。DeepSeek 的 Watchdog 是独立 agent 会话，AgriDx 近期可以用确定性规则版先行，模型判断版是远期。
- **成本警示（推断，与 GAP 笔记呼应）**：Super-agent 用 2–4 倍 token 换 p50 快约 39%、p95 快约 47%。AgriDx 生产走 DeepSeek、按 token 计费，任何并行化（GAP 的同层并行、这里的多 Worker）都必须用 GAP 笔记里的 cost-of-pass（单次成本 ÷ 成功率）来算账，不能只看速度。直通“省 token 不省时间”的发现也提示：AgriDx 的跨轮复用首先要算 token 账，其次才是时间账。
- **报告形态（推断）**：群聊渠道“每条回复硬上限 100 词、轻打扰、直接给结论”，GitHub/邮件/文档渠道“结构化、 dense、含完整背景与验证结果”——这正好对应 AgriDx 的两种输出：面向用户的诊断摘要应短（结论先行），结构化证据与验证细节放另一层。现有回答模板可以按这个分层收紧。
- **要警惕的地方（推断）**：这是一篇架构探索，不是产品功能；README 明确写着“研究原型、非正式产品”“部分设计是未来方向、原型里没有实现”，且“发布代码与内部版本及文章描述的实现并不相同”。实验是合成负载、编码能力被模拟掉，p50/p95 数字不能平移到诊断场景。安全一节是全篇最值得认真对待的部分：AgriDx 目前只有用户直接输入，不可信输入面小；但如果将来接外部触发（CI、消息、定时任务），必须先有 allowlist 与“凭证 agent 可用但不可见”的机制，不能先接后补。

### 对 AgriDx 最直接的一条借鉴（推断）

先做两件不改架构的事：① 诊断循环加一条“进展看门狗”确定性规则——同一主题重复检索或连续两轮无新证据即停、降置信度并转人工；② 长期记忆召回改成 Chain of Recall 式——存摘要 + ID 链，按需逐跳展开，而不是整段塞进上下文。

## 二、深度学习 / 故障诊断方向：多智能体 LLM 协同工业设备故障诊断（fault-agents-ai4i）

- 标题：基于人工智能大模型多智能体协同的工业设备故障诊断与运维决策方法（论文配套代码仓库）
- 仓库：wangwnejie/fault-agents-ai4i（2026-11-04 创建，0 星，代码 MIT 许可，数据集 CC BY 4.0）
- 链接：https://github.com/wangwnejie/fault-agents-ai4i
- 数据集：AI4I 2020 预测性维护数据集（UCI Machine Learning Repository，DOI: 10.24432/C5HS5C；原始出处 Matzka S. Explainable artificial intelligence for predictive maintenance applications. AI4I 2020: 69-74）

### 核心方法（原文结论，以本次读到的代码与结果文件为准）

1. **四智能体分工（agents.py、prompts/coordinator.txt，原文结论）**：
   - 数据感知智能体 `perceive`：读取原始测量值并构造物理量——温差 ΔT = Tp − Ta、输出功率 P = 2πnM/60、刀具载荷累积量 W = 刀具磨损时间 × 扭矩。
   - 机理诊断智能体 `mech`：4 条设备知识规则（knowledge_base.md，来源为 AI4I 2020 数据集文档给出的故障生成机理）——R1 散热故障 HDF：ΔT < 8.6 K 且转速 n < 1380 r/min；R2 功率故障 PWF：P < 3500 W 或 P > 9000 W；R3 过载故障 OSF：W > 11000（L 型）/ 12000（M 型）/ 13000（H 型）min·N·m；R4 刀具磨损故障 TWF：刀具磨损时间约 200～240 min 时随机发生（用作换刀预警，阈值 200 min）。另有随机故障 RNF：以 0.1% 概率随机发生，无法由测量值预测。
   - 机理证据 `evidence`：输出各机理指标相对阈值的**裕度**（margin），负值表示越限（m_dT、m_n、m_Pl、m_Ph、m_osf、m_tw），并附各规则的 0/1 触发标志。这是“规则输出连续化证据”的关键设计。
   - 数据诊断智能体 `data_agent`：二元相关法处理多标签——先训一个故障判别随机森林（300 棵树），再为每类故障各训一个二分类随机森林（200 棵树），`class_weight='balanced_subsample'`，概率阈值 0.5；仅当故障判别器判定故障时才输出类型，可同时输出多类。
   - 运维决策智能体 `decide`：返回处置措施（计划检修、更换刀具或继续运行）及依据。
   - 协调智能体（prompts/coordinator.txt，全文 30 行）：职责是“根据运维人员的请求调用专业智能体完成设备诊断，并撰写运维报告”。硬规则四条：① 先输出调用计划，再根据各智能体返回的消息撰写报告；② 每个智能体的输入必须来自请求或前序智能体的输出；③ 请求缺少设备编号或时段时，先向用户询问，不得猜测；④ 报告中的数值必须直接引用智能体消息，不得自行计算或编造；⑤ 机理证据与数据诊断结论不一致时，须在报告中提示。输出格式：调用计划为 JSON 数组，每项 `{"step":序号,"agent":智能体名称,"args":{参数},"depends_on":[依赖步骤]}`；运维报告分结论、依据、措施 3 部分，不超过 200 字。
2. **协同方式（run_lib.py `collab`，原文结论）**：不是投票、不是 LLM 再判断，而是把机理证据（裕度）拼到原始特征后面，一起喂给随机森林——即**规则证据作为特征**。输入组合分三档：raw（6 个原始测量值）、phys（raw + ΔT、P、W 三个物理量）、evid（raw + 全部机理裕度证据）。
3. **实验设计（exp_main.py，原文结论）**：10 次分层随机划分（test_size=0.3，random_state=2026，按“是否故障 + 机型”分层），固定种子可复现。Exp1 主实验：知识误差 ±10%（每个阈值乘以 1+ε，ε~U(-0.10, 0.10)，模拟现场专家经验的不精确性）下五种配置对比——数据智能体、数据智能体+物理特征、机理智能体（精确知识）、机理智能体（近似知识）、多智能体协同。Exp2 知识误差扫描：误差幅度 0 / 5% / 10% / 20% / 30% 五档，对比纯规则与协同的 F1。Exp3 标签稀缺：训练量 5% / 10% / 25% / 50% / 100% 五档，对比三种数据配置的 F1。
4. **基线结果（results/res_baselines.json，10 次平均，原文结论）**：RF|raw F1 0.652（P 0.907 / R 0.510）；RF|phys F1 0.845（P 0.943 / R 0.767）；RF|evid F1 0.851（P 0.937 / R 0.781）；GBDT|phys 0.856、GBDT|evid 0.861；SVM 各档 F1 仅 0.50–0.54（精确率低至 0.35–0.40，召回率虽高但误报严重）；MLP 各档 F1 0.70–0.72。分类型召回（RF|evid）：HDF 0.959、PWF 0.961、OSF 0.818——OSF 最难。**关键对比**：加物理特征（raw→phys）RF 的 F1 从 0.652 升到 0.845（+0.193）；再加机理裕度证据（phys→evid）仅从 0.845 升到 0.851（+0.006）。物理特征工程是主要增益，裕度证据的边际增益很小。
5. **LLM 实验结果（results/res_llm_direct.json、res_llm_plan.json、res_llm_report.json，原文结论）**：模型为 Anthropic Claude Sonnet 5.5（`claude-sonnet-5-5`），采样参数取默认值，原始输出保存在 `llm_runs/out_*.json`。直接诊断（n=120，其中 52 个机理故障）：原始测量值输入 F1 0.901（P 0.980 / R 0.833，准确率 0.908），但**类型全对率仅 0.519**；含物理量输入 F1 同为 0.901，类型全对率 0.577。**多智能体协同**：F1 0.868（P 1.000 / R 0.767，准确率 0.883）——F1 低于直接诊断，但**类型全对率 0.885**，远高于直接诊断。自主规划评估（n=60）：60/60 计划正确、0 错误；其中完整请求 24、诊断请求 15、工具请求 9、询问请求 12，全部正确；一致请求 20/20；多余 decide 步骤 0。报告评估（n=20）：68 个数值 0 个无支撑，措施正确 20/20、类型正确 20/20，2 例机理—数据冲突均被正确提示；报告平均 94.1 字、最长 132 字。

### 与 AgriDx Agent 的直接相关（推断为主，逐条标注）

- **证据结构（推断）**：裕度（margin）是极好的证据形态。AgriDx 目前的诊断证据是“知识条目命中 / 未命中”的二值形态；这篇的启示是把证据连续化——每条知识 / 每项检查给出一个“离判定边界多远”的量（支持度、距离量），而不是只有命中与否。近期可先落到回答模板与离线评测：每条结论附“支持证据的裕度陈述”（例如“该症状与某故障高度吻合，但某关键区分项未提供”），未知项降置信度、不强行定性。这与第 2 次笔记里振动综述的“低置信转人工”结论互相印证。
- **协同方式的教训（推断）**：机理证据当特征拼进去，边际增益只有 +0.006，真正的大头是物理特征工程（+0.193）。对 AgriDx 的启示是：Planner / 工具层面的“多智能体协同”噱头不如先把检索到的知识做结构化——例如把知识条目转成“症状—机理—阈值/区分项”三元组再交给模型，而不是把原始文本段落直接塞进上下文。结构化先于协同。
- **协调者提示词可直接借鉴（推断）**：coordinator.txt 的四条硬规则几乎可以原样抄进 AgriDx 的系统提示词：① 缺关键信息（设备编号/时段，对应 AgriDx 的机型/症状）先问用户，不得猜测；② 报告中的数值必须直接引用工具返回，不得自行计算或编造；③ 机理证据与数据结论不一致时必须在报告中提示；④ 报告限字、分结论/依据/措施三段。这四条都不需要改代码、不需要新工具，是提示词层的改动。
- **计划格式（推断）**：调用计划的 `depends_on` 字段与 GAP 的 DAG 是同一思想的不同写法——“计划 = 带依赖的步骤图”在三篇独立来源里（PilotRL 的全局计划、GAP 的依赖图、这里的 depends_on）都出现了共识形态。AgriDx Planner 的逻辑链从模板链改成带依赖边的步骤图，是近期可落地的方向。
- **评测方法（推断）**：直接诊断 vs 协同的对比揭示了一个单看 F1 会掩盖的取舍——协同牺牲了检出率（R 0.833→0.767）换类型准确度（0.519→0.885）。AgriDx 的离线评测应同时报告“是否故障检出”与“类型全对率”两个数，而不是一个总分。另：知识误差扫描（0–30%）与标签稀缺扫描（5%–100%）是 AgriDx 评测最缺的两类实验——知识库只有 17 个合成案例、T70 仅 2 条知识条目，知识不准确与样本稀缺正是 AgriDx 的现实；做一次“知识阈值/表述扰动 ±10% 下诊断稳定性”的扫描，比扩案例数量更优先。
- **要警惕的地方（推断）**：AI4I 2020 是合成故障标签数据集，故障标签由规则生成，机理规则与标签同源，纯规则方法有“自证”嫌疑，规则方法的高分不能直接外推；RNF 随机故障（0.1%）不可预测，任何方法在它上面都是 0 召回；LLM 实验 n=120、规划评估 n=60、报告评估 n=20，样本都很小；论文正文未读到，表 3（主实验）、表 6/图 4/表 7（成本实验）的数字**未核实**，不要引用；主实验结果文件 res2.json 不在仓库 results/ 目录中（只有 baselines 与三份 LLM 评估 JSON），Exp1 的五配置对比数字本次未能从仓库取到。

### 对 AgriDx 最直接的一条借鉴（推断）

把协调者提示词的四条硬规则（缺信息先问、数值只引用、冲突必提示、报告限字）与“裕度式证据”一起落到 AgriDx 的回答模板与离线评测里——不改模型、不接传感器就能做；同时在离线评测里补“类型全对率”与“知识扰动 ±10% 稳定性扫描”两个指标。

## 本次两篇的共同点（推断）

- 两篇都指向同一个结论：**结构先于模型、证据先于结论**。Super-agent 是先定 Router/Worker/Thread/Watchdog 的结构再谈模型能力；fault-agents 是先把物理量与裕度证据算清楚再谈协同。AgriDx 近期最便宜的改进都在结构层：Planner 的依赖图、证据的裕度化、评测的分组与扰动扫描、循环的进展看门狗。
- 两篇都反对“只看一个总分”：Super-agent 用时间 + token 一起算账，fault-agents 用检出率与类型全对率分开算账。AgriDx 的离线评测口径应当同时吸收这两套：每条诊断轨迹报“是否检出 / 类型是否全对 / 轮数 / token 数 / 答对成本”。
- 两篇都给出了“诚实报告”的硬规则：Super-agent 是“草稿标未完成、失败报失败”，fault-agents 是“数值只引用、冲突必提示”。AgriDx 的回答模板应当把这两条写成不可违反的规则，而不是建议。
