## 一、深度学习 / 故障诊断方向：GraphRAG 工业故障分析（知识图谱 + 混合图检索）

- 标题：GraphRAG Industrial Fault Analysis（学位论文项目）
- 仓库：Wan-Razaq/GraphRAG-Industrial-Fault-Analysis（2025-05-25 创建，2 星，9 个 commit，本次抓取时当前 commit 678f6c4）
- 链接：https://github.com/Wan-Razaq/GraphRAG-Industrial-Fault-Analysis
- 数据：IBM3 与 IBM4 离子束机（ion beam machine）维修日志与手册排障表；原始数据、处理后数据与抽取输出均不在仓库中，仅本地持有。

### 核心方法（原文结论；以本次读到的 README、项目文档、retriever.py、chatbot_service.py、maintenance.baml 全文为准）

1. **五段管线（原文结论）**：① 预处理：把 IBM3/IBM4 维修日志按 case ID 分组；② 从日志文本与手册排障表图片中抽取结构化实体；③ 对照人工标注评估抽取质量；④ 把验证过的故障实体导入 Neo4j 建图；⑤ Streamlit GraphRAG 聊天机器人做混合图检索并生成多语言（英语/荷兰语）技师回答。
2. **图谱模型（原文结论）**：四个节点标签——`FaultLocation`（故障部位，含 machine 属性 IBM3/IBM4）、`FaultSymptom`（可观测症状，description）、`FaultReason`（原因，name）、`FaultMeasure`（纠正措施，description）；三条关系——`(FaultLocation)-[:HAS_FAULT]->(FaultSymptom)`、`(FaultSymptom)-[:CAUSED_BY]->(FaultReason)`、`(FaultSymptom)-[:MITIGATED_BY]->(FaultMeasure)`，其中 `MITIGATED_BY` 可带解决状态（Resolved/Unknown）。
3. **混合检索（原文结论，retriever.py 全文）**：用 neo4j-graphrag 的 `HybridCypherRetriever`，向量索引 `content_index`（OpenAIEmbeddings，text-embedding-ada-002）+ 全文索引 `fulltext-index`，再以一条 Cypher 遍历查询把命中节点展开成完整故障上下文：先按命中节点类型反推所属症状（从原因、措施、部位三路 `OPTIONAL MATCH` 回推，`CASE WHEN` 依次取非空者，节点本身是症状时直接取），再从该症状出发正向展开部位、原因、措施，返回拼装文本 `"部位: 症状 Cause: 原因 Measure: 措施"` 及其 score 与各节点 id 元数据。也就是说检索不是“命中一段文本就返回”，而是“命中一个节点，沿边把整条故障链取回来”。
4. **类型化抽取（原文结论，maintenance.baml 全文）**：用 BAML 定义强类型 schema（`FaultReport` 含部位、症状数组、原因数组、措施数组、解决状态）与两个抽取函数——`ExtractFaultInfo` 从维修日志文本抽取（配 5 个 few-shot 样本，含荷兰语日志原文），`ExtractFaultsFromImage` 从排障表图片抽取（硬规则：部位取表标题所示大部件而非症状里提到的子部件；措施必须与同一行同一编号的原因显式对应，不得跨原因合并；不得输出编号、分隔符等装饰）。Schema 末尾附带可运行测试 `TestExtraction`，用 `@@assert` 断言抽取结果的部位名、机型缺省、症状、原因、措施与状态。
5. **抽取评估（原文结论）**：evaluation.ipynb 对照人工标注（Doccano 标注转成的标准 JSON）计算 exact（完全一致）、partial（部分一致）、missing（漏抽）、hallucinated（编造）四类匹配，并算 precision、recall、F1 与 bootstrap 置信区间，产出 field-wise F1 分组柱状图、热力图与 missing-vs-hallucination 拆解图（仓库 `experiments/evaluation_results/` 下仅有三张 PNG 图）。
6. **回答生成与证据标注（原文结论，chatbot_service.py 全文）**：模型为 gpt-4o，系统提示词要求——用图谱上下文里的事实性内容时明确标注 `[Graph]`，无法用图谱支撑时用通用知识并标注 `[LLM]`，与离子束机无关的问题只用 `[LLM]` 知识回答；每条回答先简述问题中的关键概念/实体，再给出完整答案。图谱上下文以一条 system 消息插在**最新用户消息之前**（而不是追加在末尾）。界面在回答下方同时展示三视图：图可视化（D3.js，按节点类型着色，可缩放拖拽）、Cypher 查询、抽取实体表。
7. **工程纪律（原文结论）**：`.env`、密钥、原始/处理后数据、抽取 JSON、检查点一律不进 git；提交前要求 `git status --short --ignored` 检查；notebook 输出须清空并审查后才能提交。

### 与 AgriDx Agent 的直接相关（推断为主，逐条标注）

- **知识结构（推断）**：四节点三关系的图谱可直接映射 AgriDx 的知识组织——“部位—症状—原因—措施”正好是诊断回答的四要素。AgriDx 现有知识是扁平条目（17 个合成案例、T70 仅 2 条），近期不需要上 Neo4j：可先把知识条目改成带边的结构化记录（每条知识标明部位、症状、原因、措施四段及它们之间的指向），检索命中一条后沿边展开同一故障链的关联条目，而不是只返回命中的单条文本。这是第 3 次笔记“结构化先于协同”的同一结论在检索层的落点。
- **检索形态（推断）**：混合检索“向量 + 全文 + 图遍历展开”的三层做法对应 AgriDx 检索的缺口——目前检索只解决“找到哪条知识”，没解决“找到后把相关证据补全”。近期可落地的轻量版：命中知识条目后，把同一机型/同一部位的其他条目按“症状重叠”做一次确定性展开（带预算上限，呼应下面 eval-harness 笔记里的聚合预算纪律），再交给模型；展开是否生效要实测计数，不能只凭配置推断。
- **证据标注（推断）**：`[Graph]` / `[LLM]` 标注是 AgriDx 回答模板最值得直接抄的一条：每句结论标明“知识库有据”还是“模型常识/推断”，与第 3 次笔记的“数值只引用、冲突必提示”合起来，就是 AgriDx 回答的证据纪律。图谱上下文插在最新用户消息之前的做法也值得注意——AgriDx 目前把检索结果放在系统提示词里，多轮追问时可试验“最新一轮的证据紧贴最新问题”的排列。
- **知识库扩充方法（推断）**：BAML 的“强类型 schema + few-shot + assert 测试”是从维修日志/手册批量抽取结构化知识条目的现成范式。AgriDx 知识库扩充时可仿照：先定 `故障报告` schema（部位/症状/原因/措施/解决状态），用 few-shot 从手册与维修记录抽取，再用 exact/partial/missing/hallucinated 四类对照人工标注评抽取质量——missing（漏抽）与 hallucinated（编造）必须分开统计，因为两者在诊断里是不同的故障（漏给建议 vs 给错建议）。
- **要警惕的地方（推断）**：学位论文项目、2 星，未经生产验证；数据不在仓库，抽取质量的 F1 数值只存在于三张 PNG 图中，本次**未核实**具体数字，不要引用；用的是 gpt-4o 与 OpenAI embeddings，AgriDx 走 DeepSeek 路线需替换模型与向量模型并重测；图谱导入前有“验证过的实体”一步，即抽取结果须人工审核后才入库，AgriDx 扩知识库时也应保留这一人工关口，不能全自动入库。

### 对 AgriDx 最直接的一条借鉴（推断）

先做两件不改架构的事：① 知识条目结构化为“部位—症状—原因—措施”四段带边记录，检索命中后沿边展开同一故障链；② 回答模板加 `[知识库]` / `[模型推断]` 两级证据标注，无法用知识库支撑的内容必须标明、不得混在有据结论里。

## 二、强化学习 / 智能体评测方向：dsh-eval-harness（Agent 应用评测工具）

- 标题：dsh-eval-harness——Agent application evaluation toolkit for DeepSeek Harness
- 仓库：LTJ002/dsh-eval-harness（2026-11-04 创建，0 星，14 个 commit，MIT 许可，文档中文；本次抓取时当前 commit af8a413）
- 链接：https://github.com/LTJ002/dsh-eval-harness
- 定位：DeepSeek Harness（DSH）的插件技能包：`skills/ai-eval-harness/SKILL.md` 是给模型读的方法论，`assets/` 是可直接运行的评测实现（Python 标准库）；框架无关——任何 agent 框架只要满足“对话可编程访问 + 副作用可查询”两个前提即可用。

### 核心方法（原文结论；以本次读到的 README 全文与 SKILL.md 全文 1363 行为准）

1. **第一原则：判定依据必须是外部事实（原文结论）**：不要用 LLM 评判 LLM 做 pass/fail 门禁——同一模型家族互相打分是循环论证。可用依据按可靠性排序：数据库事实（工具实际调用了哪些、参数是什么）最高；服务端直出的结构化数据（工具返回的 JSON、卡片字段）次之；确定性规则（答案里是否出现特定事实词）居中；另一个模型的评价不能做门禁。语义质量类指标可用“经人工标注集校准过的 LLM Judge”打辅助分，单独一列、不并进门禁。按 agent 类型找外部事实源：对话 + RAG + 工具调用看审计表 TOOL_CALL 记录、服务端卡片、知识库原文事实词；编码 agent 看编译退出码与单测；多 agent 编排看任务图是否闭环、子任务产出是否被下游真读到。填不出这行就说明还没有可判定的外部事实，应先补埋点而不是先写评测脚本。
2. **第二原则：判据必须双向，且两侧代价不对称（原文结论）**：只测一个方向分数一定能刷高。应答未答（该给答案时没给，如知识库里有“48 小时”却答“请联系客服”）与不该答却答了（无依据时编造数字）都要测。作者自述本项目就栽在第一侧：系统提示词禁止回答“改期细则”，而知识库里的数字是运营确认的公开规范，检索到了也不让说，RAG 等于白做；当时评测只有“注入不得泄漏”这种单向断言，测不出该答的没答。`answer` 套件用三个字段：`mustContain`（必须出现）、`mustRefuse`（必须拒答）、`mustNotContain`（不得出现的结果形态）。两个关键局限：① `mustRefuse` 不能单用——它靠措辞词表判“是否合理拒答”，“我没有这个信息，不过地址是某某路 88 号”（先否认再编造）能同时命中词表躲过检查，必须配 `mustNotContain` 一起用；② `mustContain` 有极性盲区——“不需要提前 48 小时申请”照样命中 `48`，数字型断言要配 `expected: {value, unit, polarity}` 与 `expectedSource`（知识库具体位置），数值、单位、方向全对才算对；归一化只修表示差异（千分位、货币符号、百分号），不吞语义差异——符号、单位、数量级丢了就是事实错误。阈值按代价定：脱敏/编造类 100%，反问类允许漏判，拒答类允许误答；写死“全部 90%”是把两类不同代价混成一档。
3. **五条防误报纪律（原文结论，README 与 SKILL.md 一致，eval_online.py 固化为代码）**：① 工具是否被调用查审计日志，不看回答措辞；② 降级跳过：负向断言在空回答上恒真，不能算 PASS；③ PII 判“未打码”，不判宽禁词（正则 `(?<!\d)1[3-9]\d{9}(?!\d)` 卡数字边界，否则“脱敏成 138****1234”会被误判泄漏；“1380000”这类金额也会误命中）；④ 观测不到 → None，不进分母也不判失败（审计源没配好不能报成“agent 没调工具”）；⑤ 401/402 基础设施异常单独计 errors，退出码升 2（余额不足重试一万次也不会好，不是网络抖动）。
4. **严格度三档与基线对比（原文结论）**：`offline` 容忍 0 条（纯函数无随机性，掉 1 条就是真掉了）；`live-strict` 容忍 0 条（安全/编造类门禁：提示词泄漏、未打码 PII、越权工具调用、无依据编造业务数字；随机性解释能力波动，解释不了泄漏）；`live` 容忍 1 条（普通能力类，但必须留痕打印“波动 N 条”）。判退化用绝对条数（同分母前提），不用比率——8 条里掉 1 条是 12.5 个百分点、13 条里掉 1 条是 7.7 个百分点，同一个事实两个数字，不可比。分母变化就不判定：数据集扩了之后新旧比率不可比，正确做法是退出码 2（不可判定），要求人工核对明细后重建基线。退出码约定：0 通过、1 质量失败、2 结果不可用（路径错、数据集缺、全降级、观测不到、分母变化、401/402）。
5. **变异测试 / 负向对照（原文结论）**：绿门禁不证明任何东西，红才证明它在岗。作者实测：把 `offline` 容忍度从 0 改成 5（等于放过所有真实退化），selftest 仍然全绿——那批断言根本没覆盖自称在测的语义；补了直接断言后同一个变异会被多条断言抓到。做法是把实现改坏，看断言会不会翻红（`mutation_check.py`，逐个施加已知缺陷跑 selftest；退出码 0 = 每个变异都被某条断言抓到）。三条实现要求：① 施加变异后必须断言“替换确实生效”，否则字符串没匹配上也会全绿；② 判定逻辑必须抽成纯函数，否则没法被断言（作者踩过两次：评测器退出码内联在 `main()` 里、产品侧 `shouldRetrieveKnowledge` 内联在带二十个依赖的类里，改坏后全量测试跑两遍都是绿的；抽成纯函数后把修复回退成旧行为会精确转红 3 条、另 7 条仍绿）；③ 写测试前先确认它可证伪。变异必须在隔离环境施加（临时副本、只改副本、跑完即删，源文件全程只读）。判据固化成一句：**改完一段判定逻辑，若全量测试跑两遍都绿，先怀疑没覆盖，而不是庆祝**。README 称本地验证三项均通过（断言全过、24 个变异全部 caught）。
6. **五态结果契约（原文结论）**：统一为 PASS（测到且通过）、FAIL（测到且失败）、SKIP（符合规则的有意跳过）、ERROR（评测基础设施异常）、UNOBSERVABLE（被测行为发生了，但评测器拿不到判定所需的外部事实）；通过率分母只认 PASS 与 FAIL。关键区分：“没测到”既不能算通过，也不能算失败——全部降级时 `passed=0, tested=0`，若按 `passed == tested` 判成功，会把“什么都没测到”报成全通过；模型空回答是 ERROR 不是 PASS；审计源没配是 UNOBSERVABLE 不是“agent 没调工具”（假红）。
7. **样本量门槛（原文结论，工程经验规则、非统计分界）**：n < 5 只能报原始计数并标注“不足以支撑结论”；n < 10 百分比仅供参考（1 条 = 10~14 个百分点）；n ≥ 10 才谈得上比率；要谈可信度直接给原始计数 + 通过率及置信区间。固定输出五件套：样本总数、通过/失败/跳过计数、通过率（小 n 标注“仅供参考”）、与基线的用例级变化（哪几条新增失败、哪几条修复）、样本代表性说明。作者自述其项目 `online-multi-turn` 只有 1 条，“1/1 = 100%”的信息量就是零。
8. **运行指纹与可复现（原文结论）**：每个提示词 `.md` 算 sha256 存进 `eval/prompts-manifest.json`，测试比对不一致就红；每次在线评测另落 `eval-run-manifest.json`：runId、gitCommit、datasetVersion、模型与 temperature、promptHash、knowledgeBaseVersion、embeddingModel、chunkSize/chunkOverlap/topK、工具 schema 版本、运行时版本、apiRequestIds。temperature 非 0 或采样参数变化时，先查这里；检索链路任一环变了，基线必须重建；密钥与用户 PII 不进 manifest。
9. **工具调用评测五阶段（原文结论）**：查审计表只回答了第一问。完整判五段：① 工具选对了吗（审计表工具名）；② 参数对吗（审计表参数与服务端校验）；③ 真执行成功了吗（服务端业务结果——调了创建订单接口但服务端返回失败，任务就是失败了，“调了”不能算通过）；④ 执行结果对吗（服务端直出数据 vs 业务预期，只验证返回 200 不验证内容是坑）；⑤ 回答用了真实结果吗（回答数字 vs 服务端数据，模型编了数字但工具其实没返回过是编造）。对会改状态的写操作，额外补四类门禁：重复调用（幂等性）、异常重试、越权调用（forbiddenTools）、失败后是否编造成功文案；每类都需要在数据集里有对应用例，否则门禁只存在于文档里。
10. **多轮对话评测（原文结论）**：单轮断言全绿，多轮照样会坏：上下文丢失、指令被后续轮覆盖、多轮诱导泄漏。按场景建用例：上下文继承（第 3 轮还能用对第 1 轮的信息吗）、条件修改、多轮纠错、信息补充（必要参数缺失时追问而不是编）、状态保持、指令冲突、多轮越权诱导。判据要点：每一步都查副作用，不只判最后一条回答——中间轮调错工具、最后轮“话术圆回来”是常见假通过；安全类多轮用例同样落 `live-strict`。
11. **RAG 评测专节（原文结论）**：① 切片是否真的发生要验证而不是假设：`chunkSize` 的计量单位取决于具体切分器（LangChain `RecursiveCharacterTextSplitter` 按字符、`TokenTextSplitter` 按 token、LangChain4j `recursive` 按字符，带 EmbeddingModel 的重载才按 token），“chunkSize=800 → 约 800 个中文字才切成 2 片”是错的；结论必须落到实测——打印实际 chunk 数与每片长度，若所有切片长度都等于全文长度，说明切分从未触发。② 切片边界会切散事实：同一文档的事实跨片时向量可能只命中其中一片；解法是同文档聚合（向量检索 → Top-K 锚点 → 按 articleId 归组 → 扩展相邻切片 → 去重排序 → maxChunksPerDocument / maxContextTokens 预算裁剪），三个实现陷阱：聚合切片必须插在锚点之后（否则被末端 truncate 截掉）、回表构造 Document 必须保留 articleId（否则归组静默失效）、聚合必须有预算上限（否则长文档一次命中就把全部切片塞进上下文）。③ 语料太少时调切片参数是自欺欺人：1 篇文档、top-k=4 时库里只有 1 条可选，任何参数对比都是噪声里找规律；经验下限约 10 篇、单篇 800 字，但覆盖度比数量重要（不同业务主题、长短文档、易混淆文档、事实横跨切片边界、库里没有答案的查询、文档更新/过期/冲突场景）。④ 检索与生成要分开评：检索召回 Recall@K、排序 MRR/nDCG@K、上下文质量 Precision@K、生成忠实度 Faithfulness、引用准确性 Citation Correctness；只评“最终答没答对”会把“检索正确但模型推诿”与“检索失败但模型蒙对”混在一起。
12. **评测数据集治理与失败根因分层（原文结论）**：数据集最低治理：唯一 ID 稳定可引用（改语义换新 id、旧 id 不复用）、每条带 `why` 与 `severity`、有 `expectedSource` 的用例改知识库时同步核对判据、正反向/多轮消息数组/预期工具与参数都进数据集不埋脚本、版本与变更记录、调试集/验证集/冻结测试集三套隔离（冻结集只读，改冻结集必须换版本号并写明原因）。失败根因分八层：数据问题、检索问题、切片问题、提示词问题、模型问题、工具问题、评测问题、基础设施问题；失败明细每条尽量带根因标签，评测自身的问题也要入表（否则人们默认先查产品，评测器的错就被漏掉）。落地清单：`eval/datasets/`、`eval/baseline.json`、`eval_results.py`、`eval_baseline.py`、`eval_online.py`、`eval_rag.py`、`eval_manifest.py`、`ci-eval.yml.example`、`selftest.py`、`mutation_check.py`；selftest 与 mutation_check 是门禁的一部分，不是可选工具。

### 与 AgriDx Agent 的直接相关（推断为主，逐条标注）

- **离线评测骨架（推断）**：这是本次对 AgriDx 最直接、最完整的一套借鉴。AgriDx 目前的评测若只有“跑几个问题看答案对不对”，正好踩中本文列出的全部陷阱。近期可按三层搭起来：离线层（纯函数断言：知识命中、数值引用、拒答形态，可进 CI）、在线层（真打 DeepSeek：tool/inject/answer 三套件）、基线对比（按绝对条数判退化、安全类零容忍）。这套骨架不需要新模型、不需要生产改动，是离线工作。
- **双向判据补缺口（推断）**：AgriDx 评测数据集应同时有两组用例——“库里有答案，问法问到它”（测该答未答：检索到了却推诿、或提示词规则与知识库互相矛盾导致该答的没答）与“库里没有答案”（测不该答却答了：编造参数、编造措施）。再配 `expectedSource` 把每个期望答案钉到知识库具体条目；数字型期望要同时写数值、单位、极性（如“扭矩下降”与“扭矩上升”方向不能混）。
- **五态契约与分母纪律（推断）**：AgriDx 评测结果应按 PASS/FAIL/SKIP/ERROR/UNOBSERVABLE 五态报数，8 秒超时、DeepSeek 限流、知识库未命中导致无法判定的一律不进通过率分母；全降级（例如某次评测全部超时）时不得报“通过率 100%”或“0%”，应报“不可判定”。小 n 规则尤其适用于 AgriDx：知识库只有 17 个合成案例，任何“通过率”都应同时报原始计数（n < 10 时百分比仅供参考），不能只报一个百分比。
- **变异测试（推断）**：AgriDx 每次改评测判据（例如改“命中”的定义、改去重规则）后，应跑一次变异测试：把判据故意改坏（如把“必须命中”改成“恒真”），看评测敢不敢红；若全绿，先怀疑判据没覆盖，而不是庆祝改动没退化。这条纪律的成本很低（改几行断言），但能防止“评测全绿、线上仍错”的假绿。
- **工具调用五阶段（推断）**：AgriDx 的工具评测不能停在“调没调工具”。按五阶段判：选对工具了吗、参数对吗、真执行成功了吗（检索返回了内容？）、结果对吗（返回的知识与问题相关？）、回答用了真实结果吗（答案里的数字/措施能在工具返回值里找到吗）。第 5 段直接对应 fault-agents 笔记里的“数值只引用”规则。
- **多轮评测（推断）**：AgriDx 是多轮对话诊断，单轮评测全绿不能证明多轮可用。应单独立多轮套件：上下文继承（第 3 轮追问还能用对第 1 轮的机型/症状吗）、条件修改（用户改了症状描述，后续轮是否按新条件执行）、信息补充（缺机型/缺关键症状时追问而不是编）、多轮诱导（前几轮建立信任后诱导编造）。每一步查工具调用副作用，不只判最后一条回答。
- **RAG 专节的直接命中（推断）**：AgriDx 检索层面的三条纪律可直接抄：① 切片/分段参数先查计量单位、再实测生效（若知识条目本身很短，分段可能从未触发，所谓“切片参数调优”就是自欺欺人）；② 同文档聚合思想对应“命中一条知识后把同一故障链的其他条目补全”，聚合必须插在锚点之后且有预算上限；③ 检索与生成分开评——AgriDx 应分开报“该找的知识找到了吗（Recall@K）”与“答案是否忠于检索内容（Faithfulness）”，否则“检索坏了但模型蒙对”会被端到端分数遮住。
- **运行清单（推断）**：AgriDx 每次在线评测应落一份 manifest：git commit、数据集版本、模型（deepseek-flash）与 temperature、提示词 sha256、知识库版本、topK、工具 schema 版本。否则“为什么这次和上次结果不一样”无从查起——这正是生产同步多次出现“版本 API 返回旧缓存”式困惑时最缺的东西。
- **要警惕的地方（推断）**：0 星、2026-11-04 新建的个人项目，方法论来自作者在自己项目上的踩坑实录，不是同行评审论文；README 称“24 个变异全部 caught”与三项本地验证通过，本次**未核实**（未本地运行）；数据集样例来自摄影订单项目，接入 AgriDx 必须整体替换为农机诊断内容，判据引擎本身可复用；其中 Java/JUnit、PowerShell、Maven 的部分与 AgriDx 的 Python/Node 栈无关，只取方法论。

## 本次两篇的共同点（推断）

- 两篇都讲“证据可溯源”：GraphRAG 是 `[Graph]` / `[LLM]` 标注 + 图可视化/Cypher/实体表三视图；eval-harness 是判据钉到外部事实 + `expectedSource` 把期望值钉到知识库出处。AgriDx 的回答与评测应当同时朝“每句话有出处”走：回答里分清有据与推断，评测里分清测到与没测到。
- 两篇都反对“只看一个总分”：GraphRAG 把 missing（漏抽）与 hallucinated（编造）分开统计、按字段报 F1；eval-harness 用分层指标（检索/生成分开）、双向判据、绝对条数与五态报数。AgriDx 的离线评测口径应当同时吸收这两套：每条诊断轨迹报“是否检出 / 类型是否全对 / 轮数 / token 数 / 答对成本”，再按根因层拆失败数。
- 两篇都强调“先验证机制真生效，再谈效果数字”：GraphRAG 的抽取评估是实测四类匹配；eval-harness 的变异测试与切片实测都是在问“机制本身在工作吗”。AgriDx 的 Planner/检索/去重改动也应先证明机制生效（如聚合是否真触发、去重是否真去掉了重复调用），再谈效果数字。
- 两篇的落点都不需要新模型、不需要生产改动：GraphRAG 的图谱结构与证据标注可先落到知识结构与回答模板；eval-harness 的评测骨架可先落到离线评测。两者都是离线/提示词层的工作，与第 3 次笔记的“结构先于模型、证据先于结论”互相印证。
