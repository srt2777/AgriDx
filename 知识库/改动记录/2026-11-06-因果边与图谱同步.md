## 派生数据：因果边（新增文件，不属条目）

| 文件 | 内容 | 规模 |
| --- | --- | --- |
| 知识库/整理后的知识库/农用拖拉机知识库/causal-edges.json | 症状→候选原因→措施→阈值（有才填），每条带 `source_id` + 页码 + `evidence_kind`，强度只标“故障表候选” | 2050 条边，1453 个症状条目，7 条带阈值 |
| 知识库/工具/抽取因果边.py | 确定性文本抽取器，不调用 LLM，不自由生成；抽不出留空 | 见下“抽取规则” |

抽取规则（已实现并经 3 轮 50 条人工复核，见 `docs/knowledge-causal-edges-review.md`）：

- 只从 `entry_type` 为“维护/故障知识”的已有知识卡抽；原因字段优先级为
  原表可能原因、故障表可能原因、可能原因选摘、可能原因、离合器打滑的可能原因、
  此页列出；措施字段为针对处理、手册处理方向、原文处理方向、原文方向、
  维修建议、该手册的特定流程；症状取“故障现象”字段或条目标题。
- 编号列表（潍泰式“（1）（2）…”）原因与措施按原编号一一配对；
  融合字段（6M 等“候选与相应处理概述”）专案解析，引导头整段去掉，
  引导词认表列 / 本表列 / 本页表列 / 候选为 / 候选含 / 候选涉及 / 候选包括 /
  本表指向 / 表N-M列；“以及”先换顿号再切分；“X为候选”去尾；
  “先区分X和Y”拆成两条候选；处置性开头（先核 / 按本册 / 本表要求 / ERROR-）
  与“表N-M将……列为候选”写法一律留空。
- 潍泰 TT 单候选字段“X（原表候选，尚非确诊）。”整句作一条原因；
  边界说明（“原表另在故障列写……”“该行故障栏实际写……”等）与引号/括号
  不成对的碎片一律丢弃。
- 阈值仅当措施原文出现数字 + 单位（分钟 / 小时 / 秒 / ℃ / °C / MPa / kPa / bar /
  r/min / mm / cm / m / V / A / % / L / N·m）时取第一处原文短语，否则 null。
- 跳过（故障条目 2108 条）：no_cause 479（464 条无原因字段 + 14 条融合字段解析不出
  + 1 条原因全是边界说明 KB-JD-5E-D0-085）、no_remedy 8、no_pages 168（无页码网页源）、
  no_section 0。50 条人工复核最终 50/50 通过。

   测试文件、复核记录与本改动计划（本批提交内新增文件）。
2. **恢复哪个文件版本**：被改的 `校验索引.py`、服务端 / 前端既有文件、两份 `docs`

   `entries.jsonl` / `sources.json` / `hierarchy.json` / `kb-version.json` 本批未动，无需恢复。
3. **执行方式**：首选 `git revert <该批提交 SHA>`；若其后已有后续提交压上，改用反向
   改动计划逐项恢复。禁止用 `force-push` 改写已合入 `main` 的历史。
4. **回滚后验证**：重跑 `python3 知识库/工具/校验索引.py` + `npm test` +
   `npm run build:server` + `npm run verify`，并核对 `/api/health` 计数。
