## 0. 一句话

**单片机不跑智能体本身，只做交互终端；司稼智能体仍跑在正式站（agridx.xyz）上；机器人通过 WiFi 调正式站的诊断接口，屏幕上问答。**

已验证（2026-11-09 00:40 实测）：不带 Origin 请求头的 `POST https://agridx.xyz/api/chat` 返回 HTTP 200，约 18 秒出答案。单片机裸 HTTP 客户端默认不带 Origin，正好符合服务器的同源检查（只拦带错 Origin 或 `sec-fetch-site: cross-site` 的请求）。

## 1. 总体架构

| 位置 | 跑什么 | 说明 |
|---|---|---|
| 机器人（终端） | 触摸输入、屏幕显示、组问题、发请求、展示答案与依据、状态提示 | ESP32-S3-N16R8 + 3.2 寸触摸屏 + INMP441 麦克风 + MAX98357A 功放 |
| 正式站（服务器） | 大模型（DeepSeek）、记忆、Planner、工具调用、知识库 13,236 条、知识图谱 | 已上线，国内可直接访问 |
| 链路 | WiFi → HTTPS POST `/api/chat` → JSON 回答 | 回答约 15–20 秒 |

为什么不把智能体塞进单片机：大模型、1.3 万条知识库、记忆和规划器都在服务器上，单片机存不下也算不动。终端 + 云端是标准做法，现场对照正式站能证明是同一个智能体。

**回答时间与回退（实测提醒）：** 这次实测问“拖拉机发动机启动困难怎么办”，18.3 秒返回，但走了本地备用引擎（外部 AI 返回未通过来源或安全检查，保留本地安全建议）。界面必须有“思考中”状态，回退时要如实显示，不冒充 AI 回答。

### 与原方案的出入

- **屏幕从 3.5 寸改成 3.2 寸**：分辨率从 480×320 变成 320×240，界面要按 320×240 重排（字号和按钮都小一圈）；驱动从 ILI9488 换成 ILI9341（TFT_eSPI 里选 ILI9341 驱动，`User_Setup.h` 按实物配置）。
- **语音硬件已买**：麦克风和功放都到了，一期就能把语音收发硬件接好；但语音识别（STT）还是软件工作，排在问答联调之后，不堵主线。
- **供电从充电宝改成 18650 模块**：注意 18650 充电别无人看管；整机峰值电流到货实测，5V 输出不够就换大电流模块。

## 3. 软件

### 3.1 框架

**LVGL + TFT_eSPI（驱动层）+ XPT2046_Touchscreen + ArduinoJson。** 之前写的是 TFT_eSPI 手绘，改成 LVGL，原因：要复刻旧版网页风格，LVGL 有现成的样式、圆角、滚动、按钮状态，画出来最像网页；8 MB PSRAM 够配双缓冲。TFT_eSPI 只负责把 LVGL 的显存刷到屏上。

LVGL 配置要点：`LV_COLOR_DEPTH 16`（RGB565）；显存放 PSRAM，双缓冲各 320×40 行左右；触摸用 XPT2046 驱动对接 `lv_indev`；横屏（`TFT_ROTATION` 按实物方向调）。

**ESP32-C3 过渡版（同一版本，另一个编译环境）：** 手头有 C3 时先拿它顶着用：`pio run -e esp32-c3-devkitm-1`，4MB Flash、单 app 分区、无 OTA；S3 到了换回 S3 环境重编重烧。不是新版本，版本号不变。引脚与编译方法见 FLASHING.md §9。

### 3.2 接口（已实测通路）

- 地址：`POST https://agridx.xyz/api/chat`
- 请求头：`Content-Type: application/json`。**不要加 Origin 头，也不要加 `sec-fetch-site`**（加了错的会被服务器 403 拦掉）。
- 请求体：
  ```json
  {"messages": [{"role": "user", "content": "拖拉机发动机启动困难怎么办"}]}
  ```
  可选字段：`machineType` / `brand` / `model`（机型信息，传了诊断更准）。
- 返回：OpenAI 风格，答案在 `choices[0].message.content`；另有 `knowledgeSources`（依据来源）、`answerMode`、`provider`、`diagnosisTrace`。
- 超时：设 60 秒（正式站 CDN 回源已放宽到 60 秒，AI 回答约 16–20 秒）。失败重试 1 次；再失败显示“网络不通/回答超时，请重试”，不显示假答案。
- 多轮对话：把历史 `messages` 一起发（最近 10 轮内）；不同机器用 `sessionId` 隔离。

### 3.3 界面布局（320×240 横屏，三区）

- **顶栏（高 28px）**：左“司稼 · 智能运维”，右在线状态（绿点 + “在线”/“离线”）和时间；底边 1px 细线分隔。
- **对话区（中间，滚动）**：用户问句右对齐浅绿气泡，回答左对齐白卡片；回答下方一行小字“查看依据与核对项 ▾”（默认收起，点开列来源，和正式站一样）。
- **底部（高 56px）**：一行横滑的预设问题按钮（“发动机启动困难”“水温高怎么办”“变速箱异响”“保养周期”）+ 一个输入框占位（点开再做屏幕键盘，二期）。
- 首页就是对话区空态：中央放司稼标题 + 一行简介 + 3–4 个预设问题大按钮，点一下直接问。
- **按 320×240 横屏排，按钮两列，字号别小于 16。**

### 3.4 显示方案：为什么单独做，不直接显示网页

**结论：单独做原生界面，照旧版风格画。**

- **ESP32 上没有浏览器**：不存在能跑的 HTML/CSS/JS 渲染引擎；旧版是 React 单页应用，JS 包几 MB，需要现代浏览器 + 大量内存，单片机跑不起来。
- 直接显示网页唯一现实的路是换硬件：树莓派 + Chromium kiosk 模式。但 320×240 的屏上，旧版桌面工作台（左侧边栏 + 多栏）根本没法看，要重做响应式；而且已买的 ESP32 硬件作废，成本、功耗、开发量都上去，3 周交不出来。
- “投屏”思路（服务器渲染网页截图、串流到单片机显示）技术上能做，但延迟大、触摸要回传坐标映射，实现复杂，不适合 3 周交付。
- 原生界面 + 同一个 `/api/chat`：外观照旧版画，答案和网站一致，现场对照正式站同问同答，一样能证明是同一个智能体。

### 3.5 旧版视觉规范（从仓库旧版 CSS 实测提取，可直接抄进 LVGL）

旧版（UI1.14）是浅底扁平风：近白微绿底、深绿文字、草绿主色、细边框、圆角 8px、**无阴影、无渐变、无动画**。配色全部来自仓库 `src/ui/classic-system.css` 与 `radix-tokens.css`：

| 用途 | 网页色值 | RGB565（屏上用） |
|---|---|---|
| 页面底 | #FBFDFC | 0xFFFF |
| 卡片底 | #F7F9F8 | 0xF7DF |
| 次要底（按钮/输入框） | #EEF1F0 | 0xEF7E |
| 边框 | #D7DAD9 | 0xD6DB |
| 正文 | #1A211E | 0x1903 |
| 次要文字 | #5F6563 | 0x5B2C |
| 主色（按钮、强调） | #46A758 | 0x452B |
| 主色深（文字强调） | #2A7E3B | 0x2BE7 |
| 选中底 | #C9E8CA | 0xCF59 |

- 圆角：卡片/输入框 8px，按钮/行 4px；边框 0.5px 细线（屏上画 1px）。
- 字号（网页 14px 正文 / 24px 大标题 / 12px 小字）：屏上按比例换算，正文 16px、标题 22px、小字 12px。
- 文案照搬旧版：标题“司稼”、按钮“查看依据与核对项”、等待态“正在诊断…”、状态“在线/离线”。

### 3.6 中文字库（最容易踩坑的一点，先解决）

ESP32 没有中文字体，答案是中文，不解决字库屏上全是方框。**做法：用 `lv_font_conv` 把常用汉字做成子集字体（16px 正文 + 20px 标题两档），放进 Flash。** 子集约 3000 常用字 + 数字 + 标点 + 公式符号（λ、Δ、±、×、÷、°、μ、≈），16px 一档约 200–400KB，N16R8 的 16MB Flash 够用。先做字库、点亮“你好司稼”四个字，再往下写界面。

### 3.7 答案渲染（Markdown 轻量解析）

接口返回的是 Markdown 风格文本（`**加粗**`、列表、序号、公式符号），屏上做轻量处理再显示：去 `**`、`#` 等标记，保留换行和序号；`λ、Δ、±、×` 等符号必须进字体子集（见 §3.6）；长答案分页滚动，不截断。回退到本地建议时，原样显示回退提示，不冒充 AI 回答。

### 3.8 监控页面（数据展示 / 数据可视化）

数据来源（正式站遥测接口，已核实，全部只读）：

- `GET /api/telemetry/scenario` — 当前场景（normal / coolant-rise / battery-spread / position-drift / slow-lift）。
- `GET /api/telemetry/history?channel=<通道>&window=5m|15m|1h` — 指定通道的历史曲线。
- `GET /api/telemetry/stream` — SSE 实时流，推最新采样点与告警。
- 机器人只读这三个 GET 接口，不主动切场景（切场景是 `POST /api/telemetry/scenario`，要带 expectedRunId / revision，演示切场景用网页端操作）。

**关键标注：当前服务器只有仿真源（source: 'simulated'，种子 2777），机器人上还没有真实传感器。页面常驻“模拟数据 / 仿真监测”标记，数值不冒充真实传感器读数。演示时可切 coolant-rise 场景，看水温曲线抬升和告警出现。**

布局（320×240 横屏，两页）：

- 监控总览：顶栏“司稼 · 监控”+ 在线状态 + “模拟数据”标记；三个表盘卡（水温、机油压力、转速：数值 + 单位 + 正常/注意状态）；一行“场景：正常运行 · 更新于刚刚”；一行告警横条（无告警时显示“暂无告警，全部正常”）。
- 趋势详情：水温趋势折线图（近 5 分钟，阈值 95°C 虚线）+ 告警列表（时间 + 内容 + 注意/已恢复）。

LVGL 控件：表盘用 `lv_meter`（弧形刻度 + 指针/数值），趋势图用 `lv_chart`（折线，Y 轴 60–100°C，阈值线用 `lv_line` 画虚线），告警列表用 `lv_obj` 行 + 状态文字；配色、圆角沿用 §3.5 的旧版规范。

刷新方式：首选 SSE 流（`/api/telemetry/stream`）实时推；断线或流异常时降级为每 5 秒轮询 history（5m 窗口）+ scenario；断网显示“离线，显示上次数据”并标时间，不编新数。

以后接真实传感器：界面按通道 id 抽象（水温/油压/转速只是三个通道），换数据源不用改界面。真实传感器要另做采集上传通道——当前服务器只有仿真源（TELEMETRY_MODE=simulated），真实数据进正式站需要新增采集接口，不在本次范围；机器人本地也可以先接传感器直读（ESP32 ADC/I2C），走同一套表盘和曲线控件。

遥测通道的具体 id 列表不编：仓库里通道由仿真配置定义，固件开发时以 `GET /api/telemetry/scenario` 返回的 catalog 为准。

- 0.96 寸 OLED 上监控只显示三行关键值（见 §2.3），不画表盘和曲线。

### 3.9 联网自动更新（OTA，本版已有）

- **WiFi 凭证存 NVS**：首次开机从 `secrets.h` 取 SSID/密码存进 NVS（命名空间 `sijia`，键 `ssid` / `pass`），以后联网只读 NVS；OTA 升级不碰 NVS，升级后不断网。换热点要整片擦除重烧（见 FLASHING.md §8）。
- **版本检查**：联网后约 10 秒查第一次，之后每 24 小时查一次分支上的 `version.json`（`robot/firmware/rv0.1.0/version.json`），远程版本号更新才升级（数字分段比较，0.1.10 > 0.1.9）。
- **下载与重启**：Arduino 自带 HTTPUpdate 经 HTTPS 下载 `version.json` 里 `url` 指向的 `firmware.bin`，校验镜像后切换分区、重启进新版；失败提示“更新失败，继续使用当前版本”，下次再试。证书不校验（演示取舍）。
- **注意**：Arduino 默认配置没有自动回滚，新版起不来只能 USB 重烧；演示前不要发布新版 `version.json`，避免现场赶上升级重启。发布新版流程与合并后 URL 改 main 的事见 FLASHING.md §8。

## 4. 交互流程

开机 → 联网 → 自检（`GET /api/health` 应返回 200）→ 首页 → 点预设问题或输入 → 发请求 → 思考中 → 显示答案 + 依据（可展开）→ 点追问继续。

异常只显示提示，不编答案。
